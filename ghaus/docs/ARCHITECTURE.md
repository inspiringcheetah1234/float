# Ghaus & Company: architecture, schema and phase plan

Practice-management app for a Pakistani tax law firm. It is the system of record and workflow layer
around FBR's IRIS portal. **It never files returns.** Built by Float AI for Ghaus & Company first; every
table carries `firm_id` so it can be sold to other firms.

## Stack

| Layer | Choice |
| --- | --- |
| Web | Next.js 16 (App Router, Server Components, Server Actions), TypeScript, Tailwind v4, shadcn/ui (vendored in `src/components/ui`) |
| Data | Supabase Postgres + Auth (email/password, TOTP MFA) + Storage, Row Level Security on every table |
| Hosting | Vercel (`ghaus/` is the project root directory) |
| AI (Phase 4) | Anthropic Claude API, server-side only, user confirms before anything is written |

## Data model

Everything hangs off **Client × Tax Year** (`client_tax_years`). Tax year N runs 1 July (N-1) to 30 June N
(`TY2026 (Jul 2025–Jun 2026)`).

Every business table has: `id uuid`, `firm_id` (defaults to the caller's firm), `created_at/by`,
`updated_at/by` (`updated_at` is the optimistic-lock token), `deleted_at/by` (soft delete).

### Tenancy, people and permissions

| Table | Purpose |
| --- | --- |
| `firms` | Tenant. Also holds firm-level settings: default number format, wealth-gap threshold, ATL surcharges and risk window, s.114C flag and thresholds |
| `roles` | Per firm. System roles: `owner`, `senior_associate`, `associate`, `clerk`; firms may add more |
| `role_permissions` | Role × module (`clients`, `returns`, `notices`, `fees`, `vault`, `settings`) → `can_view`, `can_edit`. Owner is implicit full access |
| `users` | Firm members; `id = auth.users.id`; one firm per user; role, active flag, number-format preference |

### Clients

| Table | Purpose |
| --- | --- |
| `clients` | type (individual / AOP / company), name, CNIC (`12345-1234567-1`, unique per firm), NTN, STRN, phone, WhatsApp, email, address, city, referred_by, assignee, reviewer, active, notes; `search_digits` for digit search |
| `client_registrations` | Provincial registrations (PRA, SRB, KPRA, BRA, other), many per client |
| `client_relations` | `related_client` is the `relation` of `client`: spouse, parent, child, sibling, director, partner, member, shareholder |

### Returns

| Table | Purpose |
| --- | --- |
| `client_tax_years` | One per client per year. Pipeline `return_status`, assignee, reviewer, review sign-off (by/at), filed_on, acknowledgment_no, income by head, exempt, final/fixed, taxable income, tax chargeable, withheld/paid, `payable_refundable` (generated), wealth inputs (opening, closing, personal expenses, gifts, inheritance, loans, foreign remittance, other inflows, other outflows), ATL status + last checked |
| `wealth_items` | Wealth statement lines: category, description, cost, `is_cash_equivalent` |
| `v_client_tax_years` (view) | Adds client fields, `filing_due_date` (from rules + overrides), wealth totals, `expected_closing_wealth`, `wealth_gap`, `is_filed` |

Wealth reconciliation mirrors IRIS:
`expected closing = opening net assets + declared income + exempt + final/fixed + other inflows − personal expenses − other outflows`;
`wealth_gap = closing net assets − expected closing`. Closing net assets come from the wealth statement
lines when present (assets − liabilities), else the `closing_wealth` field.

Pipeline: Not started → Documents requested → Documents received → In preparation → Under review →
Sent for client approval → Approved → Filed → Acknowledgment uploaded → Closed.

### Deadlines (configuration, never hard-coded)

| Table | Purpose |
| --- | --- |
| `deadline_rules` | kind (`annual_return`, `sales_tax_return`, `withholding_statement`, `appeal_limitation`), client types, authority, forum, due month/day + year offset, month offset + period, days after |
| `deadline_overrides` | Extension for a rule + tax year (or period) + optional client types, with the circular reference. One row moves every affected client |
| `return_due_date()` / `appeal_limitation_date()` | SQL functions; the latest override wins |

Seeded defaults (editable, flagged "Verify against current law"): individuals/AOPs 30 Sep; companies 31 Dec
(30 June year-end); monthly sales tax (FBR, PRA, SRB, KPRA, BRA) 18th of next month; quarterly
withholding statements 20th of the month after the quarter; appeals 30 / 60 / 90 days to Commissioner
(Appeals) / ATIR / High Court from receipt of order.

### Litigation

| Table | Purpose |
| --- | --- |
| `notice_sections` | Library: law, section, title, plain-language description, default reply window, reply template (Phase 4). Seeded: ITO 114(4), 116, 122(5A), 122(9), 137, 138, 161/205, 176, 177, 182; STA s.11, s.25 |
| `notices` | client, tax year, law, section, notice no, issue/received/reply-due dates, officer, RTO/LTO/CTO + city, demand, assignee, reviewer, status (received → reply drafted → under review → submitted → hearing → order → closed / appealed), sign-off |
| `hearings` | On a notice or appeal: date/time, forum, appearing team member, status, outcome, next date |
| `appeals` | Originating notice/order (or parent appeal), forum, order dates, filed_on, status, outcome; `v_appeals.limitation_deadline` |

### Work, documents, money, security, audit

| Table | Purpose |
| --- | --- |
| `documents` | Per client (optionally client-year / notice / appeal), type, Storage path in private `documents` bucket (`<firm_id>/<client_id>/…`), served by short-expiry signed URLs |
| `document_types`, `message_templates`, `pipeline_task_rules` | Settings libraries. Task rules: "on status X create task Y for assignee/reviewer due in N days" |
| `tasks` | Linked to client / client-year / notice / appeal; assignee, due, status; `auto_rule_id` when created by the pipeline |
| `comments` | On client / client-year / notice / appeal, with `mentions uuid[]` → notifications |
| `notifications` | In-app, per user |
| `fee_agreements`, `invoices`, `payments` | PKR. `v_invoice_balances` for receivables and aging |
| `credentials` | IRIS / provincial logins; `secret_ciphertext` (AES-256-GCM, key in env). App users cannot `SELECT` that column at all |
| `activity_log` | Every insert / update / soft delete / restore (with before, after, changed fields, actor) plus explicit `reveal` and `export` events |

### Enforcement in the database (not just the app)

- **Tenancy**: RLS on every table: `firm_id = app.firm_id()`. Module rights via `app.can(module, 'view'|'edit')`.
  Foreign keys bypass RLS, so `app.check_firm_refs()` rejects references to another firm's rows.
- **2FA**: `app.firm_id()` returns NULL for the owner and vault users unless the session is `aal2`, so
  they see nothing until they verify TOTP.
- **Soft delete**: app users have no `DELETE` privilege.
- **Review gate**: triggers block a return from passing Under review, and a notice reply from
  becoming Submitted, without sign-off by the assigned reviewer (or an Owner). Sending work back
  clears the sign-off.
- **Auto-tasks and notifications**: triggers on pipeline moves, reassignment and @mentions.
- **Audit**: `app.audit()` on every table; secrets are stripped.
- **Optimistic locking**: updates filter on the `updated_at` the user loaded; zero rows → conflict prompt.

## Phase plan

The brief does not split the work into phases beyond naming AI as Phase 4, so this is the proposed split.
The **whole schema** (all phases) lands in Phase 1 so later phases are mostly UI.

**Phase 1: foundation, clients and the returns workflow** (this delivery)
- Schema, RLS, triggers, seeds, pgTAP tests
- Auth: sign in, create firm, TOTP 2FA enrol/verify enforced for owner and vault roles
- App shell: sidebar, Cmd+K command palette, notifications, PKR lakh/crore toggle, DD-MM-YYYY dates
- Settings: firm (thresholds, ATL surcharges, s.114C flag), users, roles & permission matrix, deadline
  rules & overrides, notice section library, document types, message templates, pipeline task rules
- Clients list with fast search (name, CNIC, NTN, phone), filters, bulk reassignment, create/edit, soft delete
- Client 360: header (IDs, ATL badge, assignee/reviewer, last edited), tab per tax year with return
  figures, status + sign-off, wealth statement + reconciliation + year-over-year trend, tasks,
  comments with @mentions, activity
- Filing-season kanban with filters, drag to move, review gate errors surfaced, "start season" bulk create
- Review queue, tasks, Today (owner) and My Work dashboards

**Phase 2: documents and litigation**: document upload / signed URLs, notices & litigation board,
notice review gate UI, hearings calendar by team member, appeals with limitation deadlines, ATL tracker,
s.114C checker (behind the flag), Workload screen.

**Phase 3: money and security**: fees, invoices, payments, aging; credentials vault (AES-256-GCM,
Reveal with 30-second auto-hide and audit); daily digest email (Vercel Cron); per-client ZIP and
full-firm Excel export.

**Phase 4: AI**: document figure extraction, notice intake, reply drafting, always confirmed by a user
before anything is written.
